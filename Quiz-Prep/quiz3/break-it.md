For Vulnerability 1, I intentionally created a SQL injection flaw in a copy of my app rather than my live site by changing the safe prepared statement in breakit_copy/api/save_score.php into a direct string concatenation query. The vulnerable code looked like this: $sql = "INSERT INTO scores (player_name, mode, difficulty, score, total_questions, performance_title) VALUES ('" . $playerName . "', '" . $mode . "', '" . $difficulty . "', '" . $score . "', '" . $totalQuestions . "', '" . $performanceTitle . "')"; $pdo->exec($sql); and this is dangerous because the player name gets inserted straight into the SQL command instead of being safely separated from it. A specific malicious input someone could type into the player name field is Hacker', 'general', 'hard', '999', '10', 'Hall of Fame') #, which would close the first value early and inject fake values into the rest of the query. If that happened, my database would save a fake leaderboard row instead of the real quiz result, meaning an attacker could make the leaderboard show false scores and corrupt the data. My original safe code used a prepared statement with placeholders and execute(), which looked like this: $stmt = $pdo->prepare("INSERT INTO scores (player_name, mode, difficulty, score, total_questions, performance_title) VALUES (:player_name, :mode, :difficulty, :score, :total_questions, :performance_title)"); $stmt->execute(['player_name' => $playerName, 'mode' => $mode, 'difficulty' => $difficulty, 'score' => $score, 'total_questions' => $totalQuestions, 'performance_title' => $performanceTitle]); and this prevents the attack because PDO treats the user input only as data, so even if someone types SQL syntax, it is stored as plain text instead of being run as part of the command.

For Vulnerability 2, I chose XSS and created the problem in my practice copy by removing the escaping from the leaderboard output in breakit_copy/js/quiz.js. The vulnerable code looked like this: row.innerHTML = \<td>${index + 1}</td><td>${entry.player_name}</td><td>${entry.score}/${entry.total_questions}</td><td>${entry.performance_title}</td><td>${formatDate(entry.played_at)}</td>;which means the player name is inserted directly into the page as raw HTML. A malicious input for this vulnerability would be<script>alert('hacked')</script>typed into the player name field, and if that gets saved and later shown on the leaderboard, the browser would run the script instead of displaying it as harmless text. In this example it would make a popup alert appear, but in a real attack it could be used to inject unwanted page content, trick users, or run JavaScript in the browser. My original safe code usedescapeHtml()around user-controlled values, likeescapeHtml(entry.player_name)andescapeHtml(entry.performance_title), which fixes the problem by converting dangerous characters such as <and>` into safe HTML entities so the browser shows the script tag as text instead of executing it. This matters because XSS attacks target the users viewing the page, not just the database, so output escaping is an important part of keeping the site safe.
